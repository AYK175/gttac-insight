# GTTAC Insight

Natural-language analytics dashboard for the **Global Terrorism Trends and Analysis Center (GTTAC)** GRID database. Ask questions in plain English — the app converts them to safe SQL, runs them against a PostgreSQL database, and visualises the results with interactive charts and geospatial maps.

**Live demo:** [gridflow-kappa.vercel.app](https://gridflow-kappa.vercel.app)

---

## Architecture

```
Browser (Vercel) ──► ngrok tunnel ──► FastAPI (localhost:8001)
                                           │
                              ┌────────────┼────────────┐
                              ▼            ▼            ▼
                           Ollama      PostgreSQL     FAISS
                        (gemma3:12b)    (GRID DB)   (RAG index)
```

| Layer | Stack |
|-------|-------|
| Frontend | Next.js 16, Tailwind CSS v4, ECharts 6, React 19 |
| Backend | FastAPI, Uvicorn, psycopg 3 |
| LLM | Ollama — `gemma3:12b` (local, no API key needed) |
| RAG | FAISS + sentence-transformers (`all-MiniLM-L6-v2`) |
| Database | PostgreSQL — GRID schema |

---

## Features

- **NL → SQL**: Type a question, get back a safe read-only SQL query generated by a local LLM
- **Auto-visualisation**: Bar charts, line charts, and choropleth world maps chosen automatically based on the query
- **RAG explanations**: Click "Explain with RAG" to get a narrative analysis grounded in GTTAC discourse documents
- **Dashboard overview**: KPI cards (incidents, casualties, killed, wounded) and six pre-built charts (regions, countries, ideologies, tactics, weapon types, groups)
- **Filters**: Incident type (Terrorist Incident / VITA / Both), region, and date range passed as SQL constraints
- **SQL safety**: Only `SELECT` queries allowed; tables restricted to the GRID schema; `LIMIT` injected automatically

## Prerequisites

- Python 3.10+
- Node.js 18+
- PostgreSQL with GRID tables: `incidents`, `perpetrators`, `tactics`, `casualties`
- [Ollama](https://ollama.com) with `gemma3:12b` pulled
- (Optional) [ngrok](https://ngrok.com) account for remote frontend access

## Backend setup

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Create a .env file
cp .env.example .env             # then edit with your values
```

**.env variables:**

```env
DATABASE_URL=postgresql://user:password@localhost:5432/grid

# Optional tuning
QUERY_TIMEOUT_MS=30000
MAX_ROWS=5000
RAG_DOCS_DIR=docs
RAG_INDEX_DIR=.rag_index
EMBEDDING_MODEL=sentence-transformers/all-MiniLM-L6-v2
```

```bash
# 4. Start Ollama (in a separate terminal)
ollama serve
ollama pull gemma3:12b

# 5. Build the RAG index (add .md / .txt docs to docs/ first)
python -m gttac_insight.rag

# 6. Start the backend
uvicorn backend.main:app --host 0.0.0.0 --port 8001
```

## Deploying (Vercel + ngrok)

Use this setup to host the frontend on Vercel while keeping the backend and LLM running locally.

**1. Expose the backend via ngrok:**

```bash
ngrok http 8001
# Copy the https://xxxx.ngrok-free.app URL
```

**2. Set the env var on Vercel (no trailing newline):**

```bash
printf 'https://xxxx.ngrok-free.app' | vercel env add NEXT_PUBLIC_API_BASE production
```

**3. Deploy:**

```bash
cd frontend
vercel --prod
```

> The frontend is statically built at deploy time, so `NEXT_PUBLIC_API_BASE` is baked in. Re-deploy whenever you restart ngrok with a new URL (unless you have a paid ngrok plan with a fixed domain).

## API endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/dashboard/summary?top_n=8` | KPI totals and top-N lists for all dashboard charts |
| `POST` | `/query/nl_run` | Convert a natural-language question to SQL and run it |
| `POST` | `/explain` | RAG-backed markdown explanation of query results |

### `/query/nl_run` request body

```json
{
  "question": "What weapons were most used in Western Africa?",
  "incident_types": ["Terrorist Incident", "VITA"],
  "region": "Western Africa",
  "date_from": "2020-01-01",
  "date_to": "2023-12-31"
}
```

## SQL safety

- Only `SELECT` (including `WITH ... SELECT`) is permitted — any other statement is rejected before execution
- Tables are restricted to: `incidents`, `perpetrators`, `tactics`, `casualties`
- `LIMIT` is injected or capped to `MAX_ROWS` (default 5000)
- PostgreSQL `statement_timeout` is enforced per connection
- LLM output goes through a post-processing pass that corrects common column-name hallucinations before execution

---

## Database schema (GRID)

```
incidents        — incident_id, incident_date, year, month, region, country,
                   state_province, city, latitude, longitude,
                   incident_type, incident_summary

casualties       — incident_id, killed_total, wounded_total,
                   perpetrator_fatalities

tactics          — incident_id, tactic_type, weapon_type, is_suicide_attack

perpetrators     — incident_id, group_name, ideology_category,
                   is_designated_fto
```

## RAG index

1. Add `.md` or `.txt` GTTAC discourse documents to `docs/`
2. Run `python -m gttac_insight.rag` to build the FAISS index
3. After running a query, click **Explain with RAG** to get a grounded narrative
